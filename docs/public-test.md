# 高并发方案与公测验证

## 项目说明口径

> 本项目已实现面向目标规模的高并发架构，采用负载均衡、无状态多实例、数据库事务及唯一约束、缓存回源保护、设备分区队列、背压和运行观测。系统采用公测持续验证实际承载能力，不开展独立压力测试。

其中“已实现”描述代码和配置。当前尚未开展公测，没有目标QPS达成记录；不得把设计目标写成实测结果，或将功能并发测试表述为公测通过。

## 原始目标与对应实现

| 原始指标 | 设计目标 | 已实现机制 |
|---|---:|---|
| 用户登录 | 2,000 QPS | 多实例入口、登录限流、Redis验证码、账号锁定 |
| 站点查询 | 10,000 QPS | 共享短缓存、回源互斥、SQL聚合及索引 |
| 设备状态查询 | 5,000 QPS | 设备异步更新、索引查询、API横向扩展 |
| 开始/结束充电 | 各1,000 QPS | 用户/设备行锁、部分唯一索引、状态机、订单幂等 |
| 设备上报 | 20,000条/秒以上 | 批量接入、16分区队列、独立Worker、ACK/重试/死信/背压 |
| AI咨询 | 1,000 QPS | AI为选做，当前未实现，明确不计入完成范围 |

注册用户、日活和同时在线人数也是原始设计目标，不是现有数据量或已经验证的容量。

## 公测部署拓扑

```bash
docker compose -f compose.yaml -f compose.public-test.yaml up --build
```

使用支持 `!reset` 的较新Docker Compose。该配置沿用演示模式；入口仍只绑定本机 `127.0.0.1:8080`，本轮没有将服务对外发布。真正组织公测时应在所选部署环境配置可访问入口、HTTPS及对应连接密钥。

- 网关后有两个API实例，各两个进程；两个Worker分别负责分区0–7与8–15。
- 应用容器不直接发布端口；仅信任同一部署网络内网关覆盖写入的转发地址头。
- 两个API实例合计四个进程，数据库池上限合计4×15=60个连接；两个Worker和一个模拟器各最多3个，合计配置预算69个。增加实例时同步调整数据库连接预算。
- Nginx当前每IP登录10r/s、业务100r/s、连接100个，是保护阈值，不是平台总容量。学校网络/NAT下多人共用IP时，应根据真实流量调整。
- 不执行自动压测、不生成批量虚假用户或交易。

## 公测中如何记录

管理员携带Bearer Token访问 `/api/v1/admin/observability`，以固定间隔保存返回JSON，并留存网关访问日志。网关日志包含HTTP状态、总耗时、上游耗时和实际命中的上游地址，可对照应用指标。

记录至少包括日期时间、部署版本、实例数、硬件配置、实际参与用户数和观察时段。报告只填写真实观察到的吞吐、耗时、错误率和积压；指标缺失应标注缺失，不填0冒充测量结果。

重点观察：

1. 找桩、扫码、预约、停止驶离和支付的实际完成情况，以及并发情况下有无重复占桩、支付、扣分。
2. 5xx与429的原因、P95桶上界是否上升；缓存重建时503是否频繁。
3. 设备队列积压是否持续增长，pending是否恢复，是否产生死信、Worker是否持续有心跳。
4. 网关是否把请求分到两个实例，实例退出后是否切换；已发送支付POST不得被网关重复发送。

后台指标属于辅助观测，采用尽力写入，不能单独作为精准容量认证。实际公测完成后另写结果记录；本说明是验证方法，不是公测结果。
